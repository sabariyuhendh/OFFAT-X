Abstract—Broken Object Level Authorization (BOLA) and Broken Function Level Authorization (BFLA) rank first and fifth in the OWASP API Security Top 10 (2023), yet they are hard to find automatically because each depends on the relationship between identities and resources. OWASP OFFAT is a useful open baseline, but its documented checks act on single requests, do not perform the setup calls many resources need, do not compare outcomes across privilege levels, and run without sandboxing. This paper presents OFFAT-X, which adds dependency-aware chaining, a role-differential matrix over four privilege tiers, semantic response diffing, sandboxed reconnaissance with a prebuilt dirb image, and remediation hints with a GitHub Action that gates merges on new findings. On a seeded benchmark and three public vulnerable APIs, evaluated over five runs, OFFAT-X reaches [recall] recall and [FPR] false-positive rate, against [recall] and [FPR] for unmodified OFFAT.

Keywords—API security; authorization testing; BOLA; BFLA; OpenAPI; dynamic application security testing; sandboxing; DevSecOps.

Introduction

REST APIs connect mobile apps, frontends, partner systems and internal services, and most sensitive data passes through them. The OWASP API Security Top 10 (2023) ranks BOLA first and BFLA fifth [1]. BOLA occurs when an endpoint returns or changes an object without checking that the caller owns it; BFLA occurs when a low-privileged caller can invoke an administrative function. Both are improper-authorization weaknesses (CWE-285, CWE-639) [9].

Automated testing struggles with them. A BOLA flaw is visible only when two identities are compared on an existing resource: a scanner that requests /api/orders/{id} with a random identifier receives a 404 and learns nothing, while one that trusts status codes misses 200 responses that carry error bodies. Two-account testing with Autorize [4] works but does not scale to hundreds of operations.

OWASP OFFAT [2] is an MIT-licensed tool that generates tests from an OpenAPI file for BOLA, mass assignment, injection and other classes. It has no stateful setup, no cross-role comparison, no tool isolation or CI-native fixes and its documentation says as much; it’s per-endpoint, single-identity checks. This paper presents OFFAT-X, which keeps OFFAT as its baseline and adds chaining (Sect. IV), a role matrix (V), semantic diffing (VI), sandboxed reconnaissance (VII) and remediation with a CI gate (VIII). Section IX gives the evaluation protocol, Section X the results, and Section XI the limitations.

The contributions are: (i) a stateful chaining engine that derives setup sequences from the specification; (ii) a four-tier role-differential matrix that separates BOLA from BFLA; (iii) a semantic differ that does not rely on status codes; (iv) a sandbox for third-party reconnaissance; and (v) CI-native reporting with remediation hints. Each is specified below with its parameters so that it can be reproduced.

Related Work

RESTler [3] infers producer–consumer dependencies from an API specification and fuzzes request sequences, but targets crashes rather than authorization outcomes. Authorize [4] replays requests under a second identity, and Auto-IDOR-Hunter [5] tracks identifier mutations in passive traffic; both act on traffic a tester has already produced. The OWASP Testing Guide [6] informs our classification rules. OFFAT-X differs by working from the specification, and by reporting in SARIF [7] over the OpenAPI contract [8]. Deliberately vulnerable APIs crAPI [12], VAmPI [13] and Juice Shop [14] supply the ground truth in Section IX. System Architecture

The pipeline is as shown in Fig. 1. Before any tests are generated, Spec ingestion normalizes OpenAPI 2.0 and 3.x [8]. The planner creates chains × roles × operations, while the sandbox provides undocumented candidate endpoints, the executor, differ and classifier label outcomes, the reporter and CI gate generate output, and an audit log provides information about each request. The generators used by OFFAT are re-used and not forked; each extension is a plugin; findings are deterministic. A scope file contains allowed hosts, tiers and rate limits, and it is read from the environment and never written to reports (as shown in Listing 1).

The pipeline is run in the following stages: (1) scope validation; (2) ingestion and normalisation of the specification; (3) if enabled, the running of the sandboxed reconnaissance; (4) building the dependency graph and making plans; (5) the running of chains by tier and identity; (6) classification of responses and scoring them; (7) generating hints and reports; and (8) applying the CI gate. If it fails at step 1, it will not proceed and will be recorded as a failure, which will prevent another request being within the allowed scope.s

Dependency-Aware Stateful Chaining

Resources are created before they are read. We build a graph G = (V, E) from the specification, with an edge (p, c) when operation p produces a resource type τ that c consumes. Producers are identified from 2xx response schemas containing an id field, and consumers from path parameters such as {orderId}. A chain is discovered by BFS from the nearest producer for a target t, bounded to four steps. Algorithm 1 executes it per tier, and a setup failure is recorded as inconclusive rather than negative, so a missing object is never taken for a secure endpoint. For example, POST /api/cart → POST /api/checkout yields an order identifier that a second identity then requests from GET /api/orders/{orderId}.

Inference is deliberately conservative. An ambiguous producer keeps a low-weight edge, and the planner reports how many targets have no chain at all, so coverage gaps are visible in the report instead of silently skipped.

Role-Differential Authorization Testing

Tiers form the ordered set R = {guest &lt; low &lt; premium &lt; admin}, and a tier may hold several identities for horizontal tests. For target t on a resource owned by identity o, the executor issues t as every other identity, producing M[t, a, o]. Table II maps each comparison to a finding class, and Fig. 2 gives the same rules as a decision path. Because many specifications omit permissions, a provisional policy is inferred: an operation is treated as admin-only when admin receives a 2xx and a lower tier receives 401 or 403. Vertical findings resting on that inference are labelled suspected; explicit policy entries override it and yield confirmed findings.

As a worked case, a low-tier identity Alice creates order 42. A second low-tier identity, Bob, requests GET /api/orders/42 and receives 200 with Alice’s line items and address. The semantic score for this response is D = 1.0 (Eq. 2), so the finding is BOLA with high confidence. If instead an admin-only operation returns 200 to a low-tier identity while the admin tier also succeeds and the lower tier receives 403 for the same operation, the policy inference marks it as suspected BFLA until an explicit entry confirms or rejects it.

Semantic Response Diffing

Status Codes Deceive: A lot of frameworks return 200 when they fail or expose the data beside a failure flag. For attacker response a and owner baseline v, the differ compares key structure K, identifier overlap V and an error signature E:

J = |K(a) ∩ K(v)| / |K(a) ∪ K(v)|

O = |V(v) ∩ V(a)| / |V(v)|

and flags the response when the score of Eq. (2) reaches the threshold τ:

D = w_k·J + w_o·O + w_s·1[2xx] − w_e·E(a)

The initial weights are w_k = 0.3, w_o = 0.5, w_s = 0.2 and w_e = 0.6, with τ = 0.7, to be tuned on a calibration service [[N]]. The verdicts these weights give are listed in Table III, and the steps of the scoring can be seen in Fig. 3 as a flowchart.

The weights are interpreted as a priority order. The most evident identifier is the owner identifier (w_o), followed by a shape identifier (w_k) and a 2xx status (w_s) which is common to many responses, with the error signature (w_e) superseding them, eliminating the 200-with-error false positives.

Sandboxed Reconnaissance

Reconnaissance tools analyze aggressive responses, and may be able to access the internal hosts. OFFAT-X thus runs each tool in an ephemeral container: the default one is a Debian base container with Dirb [10] and its wordlists pinned by digest. Candidate paths from dirb are normalised and passed through the same semantic checks, and plugins are accepted only against a validated manifest. The controls listed in Table IV are based on the Docker’s hardening guidance [11]. Fig. 4 shows the trust boundary.

All containers are destroyed at the end of their run or at their timeout. The sandbox introduces no extra cost beyond container start-up, which is measured separately in Section X, because only this is a cost the sandbox imposes on detection.

Remediation, Reporting and CI/CD

For each finding, the OWASP category, CWE, tiers, chain trace, decisive request and response, score D and confidence are recorded. If the template is deterministic and exists in the project manifest, then the fix is provided in remediation, which is shown beside the vulnerable query in Listing 2 for Node.js and Prisma. Results are output as JSON (which is compatible with SARIF 2.1.0 [7]) and as HTML.

The verdict, the score and its three terms are included in each HTML report next to the request pair that created the score, allowing the developer to verify the decision without needing to re-run the scan. The JSON form is identical to that used for tooling, and each finding in the SARIF form is associated with its operation for code-scanning platforms [7].

Listing 2.  Remediation hint for a BOLA finding

Vulnerable:

prisma.order.findUnique({

where: { id: req.params.id } })

Fix:

prisma.order.findFirst({

where: { id: req.params.id,

userId: currentUser.id } })

A composite GitHub Action (Listing 3) is executed on pull requests with changes to the specification, uploads SARIF and fails only on new Critical or High findings when compared to the default-branch baseline.

A fingerprint of operation is used to match findings between runs, not the request text; this means that a rename or a finding with a different payload does not re-open an old finding. The gate only fails if there is a fingerprint in the pull request and it is not in the baseline.

Experimental Setup

Targets. crAPI [12], VAmPI [13] and the Juice Shop API [14] provide public ground truth. An in-house multi-role service with [N] BOLA, [N] BFLA and [N] benign endpoints that return 200 with error bodies measures false positives directly. Table V summarises them.

The in-house service is written before any tool is run, and its planted flaws are listed in a ground-truth file that is hidden from the scanner’s configuration. Benign endpoints are included so that false positives can be counted on the same run as detections. A calibration service with the same structure but different planted flaws is used only to set the weights of Eq. (2).

Protocol. OFFAT is run in default mode. OFFAT-X is run in full and with each module removed. A finding matches ground truth when operation, class and tiers agree. Metrics are computed per tool:

P = TP/(TP+FP),   R = TP/(TP+FN),   F1 = (2·P·R)/(P+R),   FPR = FP/(FP+TN)

Each configuration is repeated five times; the mean, standard deviation and 95% confidence intervals [1] are reported. Each run will include the scope file, image digests and random seeds, and the test hardware will be reported with results (hardware, Docker version). Four hypotheses that are predestined: H1, chaining increases BOLA recall for chained operations; H2, the role matrix catches BFLA that OFFAT misses; H3, the differ reduces false positives, while maintaining the recall; H4, sandbox start-up adds at most [x] s per scan.

Discussion

Three trade-offs are made explicit in the design. Chaining has additional requests per dependent target and the maximum number of targets in a chain ensures that the cost remains predictable. The role matrix requires one account per Tier, which is an up-front cost not incurred by single-identity scanners. The semantic differ is replacing the one-or-zero check result with a score, which gives the developer a way to explain each component of a verdict in every report, due to the consequence of a finding being reportable.

Limitations, Ethics and Responsible Use

Chains rely on the specification, so any identifier outside of the specification cannot be captured. Inferred policies may be incorrect and be marked as suspected. The differ targets JSON; status and length are used if there is no JSON. There are no pre-provisioned accounts in each tier required for role tests, and business-logic abuse (API6) is outside of scope. The scope allowlist is used, destructive methods are “off” (disabled) by default and will only handle objects which the scanner created, credentials will NOT be saved in reports/images and an audit log tracks every request.

Threats to validity are typical of the split. The weights are fitted into the calibration service and should not be fitted on the test targets. From the outside, there are three public targets that are not all API styles and deployments. Ground truth matching is constructive, requiring class and tier annotations, and disagreements are not hidden, but are reported.

Conclusion and Future Work

The purpose of this paper was to identify the authorization flaws that single-request scanners do not account for, and to specify a new extension, called OFFAT-X, to previous work on OWASP OFFAT [2]. These mechanisms are either individually enableable, individually measurable and individually removable. The protocol in section IX is set in advance and thus results can be read without post-hoc adjustments. In addition, upcoming features include support for OpenAPI 3.1, GraphQL and gRPC, active policy inference (confirmed) and a live internal API governance evaluation.
