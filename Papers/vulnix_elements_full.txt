ABSTRACT

[62] [w:p] [style:] [drawing:no]
Modern web software development moves at a rapid pace, yet application security testing remains severely fragmented across disparate, single-purpose utilities. Development and DevSecOps teams typically manage siloed static analysis tools for source code, external dynamic scanners for production web endpoints, manual penetration testing checklists, and isolated uptime monitoring dashboards. This tool sprawl forces engineers to constantly context-switch across multiple dashboards to assess their security posture. Furthermore, conventional signature-based static application security testing (SAST) tools suffer from notorious false-positive rates ranging from 40% to 60%, overwhelming developers with low-value alerts. Most critically, existing scanners terminate their workflow at detection, leaving the arduous task of root-cause analysis, patch drafting, and pull-request creation entirely on the shoulders of overworked engineering teams.

[63] [w:p] [style:] [drawing:no]
To bridge this gap, this project develops VulnixAI, an intelligent, multi-modal security analysis and automated remediation platform. VulnixAI consolidates six core operational capabilities—repository static code analysis, dynamic website scanning, sandboxed file analysis, automated penetration testing, controlled load testing, and continuous 24/7 uptime/SSL monitoring—under a single unified architecture authenticated via zero-configuration GitHub OAuth 2.0. At the heart of VulnixAI lies a resilient dual-AI engine that pairs a high-throughput, low-cost primary inference model (Groq LLaMA-3-70B) with an automatic failover to a large-context secondary model (Google Gemini 1.5 Pro/Flash). To analyze large enterprise repositories without exceeding model token budgets, VulnixAI implements an Abstract Syntax Tree (AST) guided file-prioritization algorithm and multi-pass batching with intelligent truncation. A multi-factor severity scoring engine maps discovered weaknesses against Common Weakness Enumeration (CWE) definitions and calculates composite risk based on keyword density, exploitability, and potential system impact.

[64] [w:p] [style:] [drawing:no]
Crucially, VulnixAI closes the loop between vulnerability discovery and remediation through an automated patch generation engine. The platform synthesizes context-aware source code patches, validates them through an AST syntax parser to prevent build regressions, and automatically commits fixes to dedicated Git branches while raising documented pull requests via Octokit. In empirical evaluations conducted across diverse multi-language repositories and production web applications, VulnixAI identified 110 vulnerabilities across a representative application codebase (7 Critical, 19 High, 64 Medium, 20 Low) with zero manual configuration, successfully generated 110 automated pull-request remediations, achieved 100% request success rate across controlled load tests at 7.33 requests per second, and sustained round-the-clock uptime monitoring with dual-channel browser and WhatsApp alerting. The platform establishes an end-to-end autonomous security pipeline that drastically reduces Mean Time to Remediate (MTTR).

CHAPTER 1 INTRODUCTION

[77] [w:p] [style:] [drawing:no]
Software security has emerged as one of the most critical engineering disciplines in contemporary computer science. Modern web and cloud applications are developed at unprecedented velocities, driven by continuous integration and automated deployment pipelines that release new code to production dozens of times each day. However, this acceleration in software delivery has profoundly widened the gap between the speed of development and the capacity of security auditing. Traditional application security testing has historically been fractured across a collection of narrow, single-purpose tools: a static analysis tool to inspect source code before compilation, a dynamic web application scanner to probe live staging endpoints, a penetration testing script to test authorization boundaries, and an isolated uptime monitoring agent to observe production availability once an application ships. That structural separation made technical sense when each domain demanded a bespoke heuristic engine, but it also imposes an onerous penalty on software engineering teams who must constantly juggle four or five disconnected dashboards to assemble a coherent picture of their system's security posture.

[78] [w:p] [style:] [drawing:no]
The practical difficulty in modern DevSecOps is therefore one of human attention, fragmented context, and alert fatigue, rather than a lack of scanning tools. Conventional static application security testing (SAST) tools rely predominantly on regular expressions and abstract syntax matching rules. While such pattern matchers execute rapidly, they lack holistic semantic understanding of code execution flow. Consequently, traditional scanners flood engineering teams with false-positive rates frequently reported in the range of 40% to 60%. This overwhelming noise causes developers to lose trust in automated tools, leading directly to the dangerous phenomenon wherein genuine, critical security vulnerabilities languish unacted upon in issue backlogs.

[79] [w:p] [style:] [drawing:no]
Earlier generations of vulnerability scanners leaned heavily on rigid syntactic patterns, which are fast but tend to flood a team with findings that are not actually exploitable in runtime contexts. VulnixAI takes a fundamentally unified approach: repository scanning, live website assessment, sandboxed file analysis, penetration testing, and load testing all sit behind the same login and reporting layer. Their findings are cross-referenced so that a weakness spotted in source code can be confirmed against the  deployed application and then tracked through continuous production monitoring. The result is a single narrative about a project's security posture instead of five disconnected reports.

[80] [w:p] [style:] [drawing:no]
Recent breakthroughs in artificial intelligence—particularly large language models (LLMs) trained on vast corpuses of source code and vulnerability databases—have demonstrated remarkable capabilities in semantic reasoning, contextual comprehension, and code generation. State-of-the-art language models can inspect complex code paths, identify multi-step taint propagation, and distinguish between benign patterns and genuine exploit vectors. However, deploying large language models directly into an enterprise security scanning pipeline introduces severe engineering hurdles that single-purpose scanners never had to confront.

[81] [w:p] [style:] [drawing:no]
Building a unified scanning platform surfaces three practical engineering challenges that do not show up in narrow tools. First, a language model's context window imposes a hard ceiling on how much source code it can reason about in one request, requiring an intelligent file-prioritization algorithm and multi-pass batching strategy to keep large repositories analysable without truncation. Second, depending on a single AI provider introduces a fatal point of failure; if that provider experiences rate limits, network throttling, or service outages, scanning completely halts. Third, generating a code patch is insufficient unless it can be applied safely; every proposed fix must pass an automated syntax verification check before it is committed to a repository.

[82] [w:p] [style:] [drawing:no]
VulnixAI addresses these fundamental challenges by combining static application security testing, dynamic website scanning, sandboxed file analysis, automated penetration testing, controlled load testing, and continuous real-time uptime monitoring into a unified, multi-modal artificial intelligence platform. Built from the ground up to shorten the distance between finding a vulnerability and merging a verified fix, VulnixAI connects seamlessly with GitHub via zero-configuration OAuth 2.0. At the architectural center of the platform sits a dual-AI engine that pairs an ultra-fast, low-cost primary inference model (Groq LLaMA-3-70B) with an automatic failover to a massive-context secondary model (Google Gemini 1.5 Pro/Flash). When an engineering team selects a repository, VulnixAI's AST-guided prioritization algorithm scores and orders files by security sensitivity, ensuring that authentication routes, API endpoints, and critical sinks are audited first.

[83] [w:p] [style:] [drawing:no]
A hallmark innovation of VulnixAI is automated remediation. Every identified vulnerability is triaged through a multi-factor severity scoring engine that synthesizes keyword density, Common Weakness Enumeration (CWE) impact, and exploit reachability into actionable Critical, High, Medium, and Low tiers. For every fixable issue, the platform synthesizes a context-aware patch, verifies the code against an AST syntax checker to guarantee that no syntax errors are introduced, and automatically commits the patch to a new branch while raising a documented pull request on GitHub, closing the feedback loop between detection and repair.

[84] [w:p] [style:] [drawing:no]
Around the clock, an autonomous monitoring worker tracks registered production web applications, evaluating HTTP availability, network response latency, and SSL certificate lifespans. If an application degrades or experiences an outage, VulnixAI bypasses crowded email channels to dispatch instant alerts via browser push notifications and WhatsApp messages, ensuring that site reliability engineers and developers receive actionable notifications within seconds of an incident occurring.

[85] [w:p] [style:] [drawing:no]
The scope of this project is stated deliberately: VulnixAI is an early vulnerability detection, real-time monitoring, and decision-support platform built on measurable code semantics and runtime indicators. It does not claim to replace senior human security auditors for complex architectural reviews; rather, it aims to eliminate 90% of routine triaging overhead, suppress false alarms through deep language model reasoning, and automate the mechanical process of patch authoring and deployment.

[86] [w:p] [style:] [drawing:no]
The remainder of this report is organised as follows. Chapter 2 reviews prior work on AI-assisted vulnerability detection, dynamic web auditing, automated penetration testing, continuous site reliability monitoring, and automated program repair, and formalizes the research gap. Chapter 3 analyses the limitations of existing fragmented systems and presents the proposed VulnixAI architecture together with its operational merits and block diagrams. Chapter 4 specifies the hardware and software environments and develops the mathematical formulation of every algorithmic module. Chapter 5 describes the benchmark repository testbed, the software setup, the working procedure, and the validation tests. Chapter 6 presents and discusses the experimental results in full across all six scanning modes. Chapter 7 concludes the report and sets out the planned future enhancements.

CHAPTER 2 LITERATURE REVIEW

[88] [w:p] [style:] [drawing:no]
Automated software security analysis sits at the intersection of static code analysis, dynamic application testing, network telemetry, and machine learning. Each of these fields has contributed foundational techniques that VulnixAI synthesizes and extends. The literature review below is structured into four primary thematic areas, culminating in an explicit definition of the research gap addressed by this work.

[89] [w:p] [style:Heading3] [drawing:no]
2.1  REVIEW OF RELATED WORK

[90] [w:p] [style:Heading4] [drawing:no]
2.1.1  AI-Assisted Vulnerability Detection and LLM Source Code Analysis

[91] [w:p] [style:] [drawing:no]
The earliest generation of static application security testing (SAST) relied on lexical tokenization and syntactic pattern matching using regular expressions. These tools, while computationally lightweight, lacked any contextual understanding of execution flow or variable scoping. In a comprehensive benchmarking study, Tamberg and Bahsi evaluated classical static analysis tools against emerging neural approaches across diverse software datasets, demonstrating that rule-based scanners routinely suffer from false-positive rates exceeding 50%, while missing subtle semantic flaws such as insecure deserialization and authorization bypasses.

[92] [w:p] [style:] [drawing:no]
To overcome these limitations, the research community transitioned toward machine learning and graph neural networks operating over Code Property Graphs (CPGs) and Abstract Syntax Trees (ASTs). While graph-based methods captured structural data flow, they demanded intensive feature engineering and struggled with multi-file contextual dependencies. The emergence of Transformer-based Large Language Models (LLMs) marked a transformative paradigm shift. Zhou et al. conducted an extensive empirical study evaluating OpenAI's GPT-3.5 and GPT-4 across standardized vulnerability detection benchmarks, finding that LLMs consistently outperformed dedicated deep learning models by leveraging their extensive pre-training over diverse software repositories. GPT-4 demonstrated a superior capacity to reason about code semantics, identify taint propagation paths, and explain the physical mechanisms of vulnerabilities.

[93] [w:p] [style:] [drawing:no]
In parallel, Szabo and Bilicki investigated the practical application of GPT-style language models for web application source code inspection. Their findings revealed that prompt-driven inspection surfaced complex security vulnerabilities that  conventional commercial scanners overlooked entirely. However, their study also highlighted persistent operational bottlenecks: language models are subject to hard context window ceilings, stochastic outputs, and high API latency. When applied naively to large repositories, single-prompt models either truncate critical files or incur prohibitive operational costs. VulnixAI directly builds upon this literature by introducing an AST-guided prioritization and multi-pass batching engine that partitions large codebases intelligently, ensuring maximum semantic coverage within strict token budgets.

[94] [w:p] [style:Heading4] [drawing:no]
2.1.2  Dynamic Website Security Scanning and Runtime Auditing

[95] [w:p] [style:] [drawing:no]
Dynamic Application Security Testing (DAST) inspects running applications from the outside in, treating the target system as a black box. Classical web vulnerability scanners execute automated web crawling, inject synthetic payloads into form fields and URL parameters, and analyze server responses for signatures of SQL injection, Cross-Site Scripting (XSS), and header misconfigurations.

[96] [w:p] [style:] [drawing:no]
While DAST tools are inherently immune to source-code false positives—since they evaluate real HTTP responses—they possess notable drawbacks. Purely dynamic scanners cannot determine the exact source file or code line responsible for an observed vulnerability. Furthermore, conventional dynamic tools fail to evaluate client-side Single Page Applications (SPAs) effectively, miss deep API routes hidden behind client-side state, and offer zero guidance on source-level remediation. VulnixAI bridges this chasm by cross-referencing dynamic website scan findings with repository static analysis, correlating runtime misconfigurations (such as missing security headers or exposed sensitive directories) with underlying server configuration files.

[97] [w:p] [style:] [drawing:no]


[98] [w:p] [style:Heading4] [drawing:no]
2.1.3  Automated Penetration Testing and Load Testing in Modern CI/CD

[99] [w:p] [style:] [drawing:no]
Automated penetration testing has traditionally been bounded by static checklists and pre-scripted exploit frameworks such as OWASP ZAP and Metasploit. Recently, researchers have explored harnessing LLMs to plan and execute multi-step interactive penetration testing engagements. Deng et al. introduced PentestGPT, a specialized framework demonstrating that an LLM could effectively guide a penetration tester through the reconnaissance, vulnerability verification, and exploit generation phases of  an engagement. In a subsequent benchmarking study, Isozaki et al. evaluated LLM-driven autonomous penetration testing frameworks and observed that while models excel at identifying standard injection vectors and file exposures, completely autonomous exploitation remains constrained by hallucinations and a lack of real-time environmental feedback.

[100] [w:p] [style:] [drawing:no]
Concurrently, performance and capacity stress testing has evolved from a manual, pre-release staging ritual into a continuous quality gate. Neelapu analyzed the effectiveness of modern load testing methodologies on application scalability, emphasizing that detecting throughput degradation, resource contention, and concurrency bottlenecks early in the development lifecycle is essential to preventing production outages. VulnixAI incorporates both automated penetration testing and controlled load testing into its unified platform, structuring penetration probe evidence so that discovered flaws (such as exposed sensitive database dumps or business logic anomalies) can be directly triaged alongside code-level findings.

[101] [w:p] [style:Heading4] [drawing:no]
2.1.4  Continuous Uptime Monitoring, KPI Anomaly Detection, and Automated Program Repair

[102] [w:p] [style:] [drawing:no]
Once an application is deployed, continuous telemetry and site reliability monitoring become paramount. Yu et al. explored supervised fine-tuning for unsupervised Key Performance Indicator (KPI) anomaly detection in mobile web systems, demonstrating that subtle latency drifts and intermittent HTTP 5xx spikes often precede catastrophic cascading failures. Extending this paradigm, Jha et al. introduced an LLM-assisted anomaly detection service for Site Reliability Engineers (SREs), proving that language models can synthesize disparate log streams, error codes, and telemetry metrics into coherent incident summaries.

[103] [w:p] [style:] [drawing:no]
Simultaneously, the field of Automated Program Repair (APR) has made remarkable strides. Berabi et al. introduced DeepCode AI Fix, demonstrating that fine-tuned language models can successfully generate correct, regression-free patches for security vulnerabilities discovered during static analysis. Jimenez et al. benchmarked autonomous coding agents on SWE-bench, establishing that modern LLMs can resolve complex real-world GitHub issues end-to-end when supplied with appropriate issue descriptions and codebase context. VulnixAI synthesizes these dual disciplines by pairing continuous production telemetry (with out-of-band WhatsApp alerting) with an  autonomous patch generation and pull-request pipeline, closing the feedback loop between detection, alerting, and remediation.

[104] [w:p] [style:Heading3] [drawing:no]
2.2  CONCLUSION FROM LITERATURE REVIEW

[105] [w:p] [style:] [drawing:no]
Taken together, the reviewed body of literature establishes that while each individual facet of application security—static analysis, dynamic scanning, penetration testing, performance benchmarking, and continuous uptime monitoring—has achieved significant technical maturity, their operational value remains severely compromised by tool fragmentation. A security engineer in a contemporary organization must maintain separate vendor subscriptions, parse incompatible report formats, manually correlate dynamic findings back to raw source code, and manually draft pull requests for every single flagged issue.

[106] [w:p] [style:] [drawing:no]
The research gap addressed by VulnixAI follows directly from these findings. There exists an acute need for a unified, multi-modal security engineering platform that: (1) consolidates static, dynamic, penetration, load, and monitoring capabilities under a single zero-configuration interface; (2) implements a resilient dual-AI failover architecture that guarantees operational continuity despite single-provider rate limits or outages; (3) solves the token context bottleneck on enterprise repositories via intelligent AST-based file prioritization; (4) filters false alarms through multi-factor severity scoring; and (5) autonomously generates syntax-validated code patches that are raised directly as GitHub pull requests. VulnixAI is engineered specifically to fulfill this research gap.

CHAPTER 3 SYSTEM ANALYSIS

[108] [w:p] [style:Heading3] [drawing:no]
3.1  EXISTING SYSTEM

[109] [w:p] [style:] [drawing:no]
Application security architectures in current commercial and open-source use fall predominantly into four fragmented, isolated categories. Each category addresses a specific slice of the software delivery lifecycle but operates independently of all others.

[110] [w:p] [style:] [drawing:no]
The first category comprises standalone Static Application Security Testing (SAST) tools (such as SonarQube, Checkmarx, or ESLint security plugins). These tools inspect source code before compilation, searching for syntactic patterns, dangerous function invocations, or known vulnerable API usages. While valuable during early development, they operate entirely on static heuristics, possess no knowledge of whether code is actually reachable in production, and generate a massive volume of non-exploitable warnings.

[111] [w:p] [style:] [drawing:no]
The second category comprises Dynamic Application Security Testing (DAST) scanners (such as OWASP ZAP, Burp Suite, or Nikto). These scanners attack a deployed application from the outside, crawling web endpoints and fuzzing HTTP parameters. Because they operate strictly against running web servers, they have no visibility into the underlying source code, cannot pinpoint the exact file or line number responsible for an error, and require extensive manual setup to configure authentication sessions.

[112] [w:p] [style:] [drawing:no]
The third category comprises ad-hoc manual penetration testing and standalone load testing scripts (such as Apache JMeter, k6, or Postman collections). These tools require specialized security engineering expertise to script, execute, and interpret, making them rare and costly exercises typically reserved for major quarterly releases rather than continuous integration.

[113] [w:p] [style:] [drawing:no]
The fourth category comprises production uptime and synthetic monitoring services (such as Pingdom, UptimeRobot, or Datadog synthetic monitors). These platforms repeatedly ping production URLs to verify availability and track response times. However, they are treated as pure operations utilities, remaining completely disconnected from the security testing and code review workflows of software engineering teams.

4.3.1  Repository Ingestion and Intelligent File Prioritization Scoring

[171] [w:p] [style:] [drawing:no]
When a user signs in via GitHub OAuth 2.0 and selects a target repository, VulnixAI immediately initiates recursive tree ingestion using the GitHub REST API. In an enterprise repository comprising hundreds or thousands of source files, analyzing every file sequentially with equal weighting is computationally wasteful and mathematically impossible within standard LLM context budgets. To solve this bottleneck, VulnixAI formulates an intelligent AST-guided prioritization scoring function.

[172] [w:p] [style:] [drawing:no]
Let R denote the set of all source code files in the repository, R = {f_1, f_2, ..., f_n}. For each file f_i in R, an Abstract Syntax Tree (AST) is generated to extract structural metrics. The priority score S_priority(f_i) is defined as a linear weighted combination of four normalized security factors:

[173] [w:p] [style:] [drawing:no]
S_priority(f_i) = w_k * K_sec(f_i) + w_e * E_entry(f_i) + w_r * R_route(f_i) + w_s * S_size(f_i)

[174] [w:p] [style:] [drawing:no]
where K_sec(f_i) in [0, 1] represents the normalized density of security-sensitive keywords (e.g., 'password', 'token', 'secret', 'exec', 'eval', 'dangerouslySetInnerHTML', 'SELECT', 'query'); E_entry(f_i) in {0, 1} is a binary indicator denoting whether f_i is an application entry point (such as 'index.ts', 'server.js', 'main.py', or 'App.tsx'); R_route(f_i) in [0, 1] quantifies the ratio of public HTTP route definitions and API controllers within the file; and S_size(f_i) in [0, 1] is an inversely scaled file-size penalty favoring compact, high-density files over vast auto-generated bundles. The weighting coefficients satisfy w_k + w_e + w_r + w_s = 1.0, with default empirical weights set to w_k = 0.35, w_e = 0.25, w_r = 0.25, and w_s = 0.15. Files are sorted in descending order of S_priority, ensuring that critical attack surfaces are audited first.

[175] [w:p] [style:] [drawing:no]


[176] [w:p] [style:] [drawing:no]


[177] [w:p] [style:Heading4] [drawing:no]
4.3.2  Multi-Pass Batching and Context-Window Truncation Algorithm

[178] [w:p] [style:] [drawing:no]
Once files are prioritized, they must be partitioned into discrete inference batches that fit comfortably within the context window C_max of the primary language model. Let T(f_i) denote the token count of file f_i computed via Byte-Pair Encoding (BPE) tokenization. A naive greedy algorithm that packs files until sum(T(f_i)) &lt;= C_max risks straddling semantic boundaries or starving low-priority files.

[179] [w:p] [style:] [drawing:no]
VulnixAI introduces a multi-pass batching strategy with intelligent semantic truncation. A dynamic token threshold T_budget = gamma * C_max is enforced (with safety margin gamma = 0.75). Files whose token length exceeds an upper ceiling T_single_max (set to 4,000 tokens) undergo AST-aware structural truncation: import statements, interface definitions, exported route signatures, and function headers are preserved, while repetitive boilerplate and static asset definitions are pruned. Consecutive prioritized files are aggregated into a batch B_k = {f_{k,1}, ..., f_{k,m}} such that the total prompt tokens plus anticipated completion tokens remain strictly bounded by T_budget. Batches are dispatched asynchronously to the AI layer, with deduplication hashes computed across findings.

4.3.3  Dual-AI Inference and Dynamic Failover Mechanism

[184] [w:p] [style:] [drawing:no]
To guarantee operational high availability and eliminate single-provider vulnerability, VulnixAI implements a stateful dual-AI failover engine. The primary inference engine utilizes Groq's Language Processing Unit (LPU) architecture running Meta's LLaMA-3-70B-Instruct model. Groq delivers exceptional inference throughput (exceeding 250 tokens per second) at minimal operational expense, enabling sub-second vulnerability analysis per file batch.

[185] [w:p] [style:] [drawing:no]
However, if Groq returns an HTTP 429 (Rate Limit Exceeded), an HTTP 503 (Service Unavailable), experiences an API timeout tau &gt; 12.0 seconds, or if a monolithic file cannot be segmented without losing critical semantic cross-file context, the failover dispatcher instantly intercepts the request. The dispatcher transfers execution seamlessly to Google Cloud's Gemini 1.5 Pro model, which boasts a million-token context window capable of ingesting the entire un-truncated repository in a single forward pass. State transitions are governed by a circuit-breaker pattern: after three consecutive primary failures, the circuit trips to Open state, routing all traffic to the secondary model for an exponential backoff period before attempting a half-open probe.

[186] [w:p] [style:] [drawing:no]


[187] [w:p] [style:Heading4] [drawing:no]
4.3.4  Multi-Factor Vulnerability Severity Scoring and CWE Mapping

[188] [w:p] [style:] [drawing:no]
Every potential vulnerability returned by the AI inference layer undergoes rigorous triaging through VulnixAI's multi-factor severity scoring engine. Rather than accepting an uncalibrated LLM label, the platform computes a composite risk score R_sev in [0, 100] blending four objective mathematical indicators:

[189] [w:p] [style:] [drawing:no]
R_sev = alpha * K_kw + beta * C_CWE + gamma * E_exploit + delta * I_impact

[190] [w:p] [style:] [drawing:no]
where K_kw in [0, 100] represents keyword-level risk confirmation; C_CWE in [0, 100] is the baseline Common Weakness Enumeration severity mapped from the official MITRE and CVSS v3.1 databases (e.g., CWE-798 Hardcoded Credentials = 85, CWE-89 SQLi = 95, CWE-79 XSS = 65, CWE-200 Information Exposure = 70); E_exploit in [0, 100] measures exploitability based on route accessibility (public endpoint vs internal helper); and I_impact in [0, 100] quantifies the potential damage to data confidentiality, integrity, and system availability.

[191] [w:p] [style:] [drawing:no]
The normalization coefficients satisfy alpha + beta + gamma + delta = 1.0, with default platform weights assigned as alpha = 0.25, beta = 0.30, gamma = 0.25, and delta = 0.20 (Table 4.3). The calculated composite score R_sev maps directly to  discrete operational risk levels and automated platform actions as specified in Table 4.4.

4.3.5  Automated Patch Generation and Git Pull-Request Remediation Pipeline

[194] [w:p] [style:] [drawing:no]
A hallmark innovation of VulnixAI is its automated remediation pipeline. When a vulnerability is confirmed and scored as Critical, High, or Medium, the system initiates closed-loop program repair. The AI engine is prompted with the vulnerable code snippet, the exact line range, the discovered CWE classification, and the multi-factor severity report.

[195] [w:p] [style:] [drawing:no]
The model generates a replacement code block embodying the remediation. Before any code is committed, the patch undergoes an AST Syntax Verification Check. For JavaScript/TypeScript files, the patch is parsed using the Babel AST parser; for Python, the ast.parse() engine verifies abstract grammar; and for HTML/PHP, lightweight linters validate closing tags. If a syntax error is detected, the patch is rejected and an iterative repair prompt is dispatched. Once syntax integrity is certified, VulnixAI uses the authenticated GitHub Octokit client to: (1) create a new Git branch (e.g., 'vulnixai/fix-cwe-798-admin-credentials'); (2) commit the modified file; and (3) open a pull request against the repository's base branch with full markdown documentation, severity badges, and remediation rationale.

[196] [w:p] [style:] [drawing:no]

4.3.6  Dynamic Website Security Scanning and Controlled Penetration Testing

[198] [w:p] [style:] [drawing:no]
In addition to static source auditing, VulnixAI incorporates active runtime assessment modules. The Website Security Scanner inspects live deployed web applications over HTTPS. It evaluates HTTP response headers against OWASP guidelines, checking for the presence of Content-Security-Policy (CSP), Strict-Transport-Security (HSTS), X-Frame-Options, X-Content-Type-Options, and Referrer-Policy. It parses the server's SSL/TLS certificate chain, extracting validity start/end timestamps, issuer authority, and cipher suite strength.

[199] [w:p] [style:] [drawing:no]
The Penetration Testing module conducts controlled, active probes against verified target domains. It inspects common sensitive file paths often left accessible by deployment errors (such as '/database.sql', '/.DS_Store', '/.env', and '/phpinfo.php'). Furthermore, it executes business-logic verification checks by injecting out-of-bound numerical values (such as negative currency amounts or extreme quantity thresholds) into API forms to verify whether server-side input sanitization properly rejects anomalous inputs.

4.3.7  Real-Time Availability, SSL Health Monitoring, and Dual-Channel Alerting

[202] [w:p] [style:] [drawing:no]
Production applications demand continuous operational surveillance. VulnixAI includes an asynchronous background daemon that performs scheduled health checks against all registered production endpoints at 60-second intervals. Each health check transmits an HTTP GET request with custom User-Agent telemetry, recording three vital metrics: (1) HTTP status code (200 OK, 3xx Redirect, 4xx Client Error, 5xx Server Error); (2) round-trip network response latency (measured in milliseconds); and (3) SSL certificate days until expiration.

[203] [w:p] [style:] [drawing:no]

If a site transitions to Degraded or Down, the alerting engine immediately triggers dual-channel notifications: browser push notifications via Web Push API and urgent out-of-band messaging via the Twilio WhatsApp Business API, ensuring immediate incident response.

5.3  WORKING PROCEDURE

[228] [w:p] [style:] [drawing:no]
The operational workflow of VulnixAI is structured into six sequential steps executed whenever a security scan or monitoring task is initiated:

[229] [w:p] [style:Heading4] [drawing:no]
Step 1: Initialisation and Authentication

[230] [w:p] [style:] [drawing:no]
Step 1: Initialisation and Authentication: The user authenticates through GitHub OAuth 2.0. The platform verifies the state parameter against CSRF attacks, issues an HTTP-only secure JWT cookie with a 7-day expiration, and populates the repository dashboard with accessible repositories.

[231] [w:p] [style:Heading4] [drawing:no]
Step 2: Repository Discovery and AST Prioritization

[232] [w:p] [style:] [drawing:no]
Step 2: Repository Discovery and AST Prioritization: Upon repository selection, the back-end retrieves the complete tree via GitHub REST API, discards binary and vendor files, and calculates the priority score S_priority for all source files based on security keywords, entry-point indicators, and route definitions.

[233] [w:p] [style:Heading4] [drawing:no]
Step 3: Multi-Pass Batching and Dual-AI Inference

[234] [w:p] [style:] [drawing:no]
Step 3: Multi-Pass Batching and Dual-AI Inference: Prioritized files are grouped into token-budgeted batches (gamma = 0.75). The primary Groq LLaMA-3 engine analyzes  each batch in parallel; if rate limits or context timeouts occur, the failover circuit immediately routes requests to Gemini 1.5 Pro.

[235] [w:p] [style:Heading4] [drawing:no]
Step 4: Multi-Factor Severity Triaging

[236] [w:p] [style:] [drawing:no]
Step 4: Multi-Factor Severity Triaging: Raw findings returned by the AI are deduplicated, mapped to official CWE identifiers, and scored via the 4-factor composite formula into Critical, High, Medium, and Low tiers.

[237] [w:p] [style:Heading4] [drawing:no]
Step 5: Syntax-Validated Patching and Pull Request

[238] [w:p] [style:] [drawing:no]
Step 5: Syntax-Validated Patching and Pull Request: For each confirmed vulnerability, the remediation engine synthesizes a patch, validates syntax through an AST parser, creates a new Git branch, commits the fix, and opens a documented pull request on GitHub.

[239] [w:p] [style:Heading4] [drawing:no]
Step 6: Continuous Health and Uptime Surveillance

[240] [w:p] [style:] [drawing:no]
Step 6: Continuous Health and Uptime Surveillance: Registered web endpoints are monitored at 60-second intervals for HTTP availability, response latency, and SSL certificate validity, pushing real-time alerts via push notifications and WhatsApp.

[309] [w:p] [style:] [drawing:no]
The experimental results substantiate the central hypothesis of this project: consolidating multi-modal security analysis behind a resilient dual-AI engine drastically enhances application security while reducing developer friction. By coupling AST-guided file prioritization with Groq's high-speed inference, VulnixAI scans full-stack repositories in seconds rather than minutes, while the automatic fallback to Gemini 1.5 Pro ensures zero operational failure during provider outages.

CHAPTER 7 CONCLUSION

[312] [w:p] [style:] [drawing:no]
In this project, we designed, implemented, and empirically evaluated VulnixAI, an intelligent, multi-modal application security platform that unifies static code analysis, dynamic website scanning, sandboxed file analysis, automated penetration testing, controlled load testing, and continuous 24/7 uptime monitoring under a single coherent architecture.

[313] [w:p] [style:] [drawing:no]
VulnixAI directly resolves the chronic tool sprawl and alert fatigue that characterize modern DevSecOps. By replacing brittle regex pattern matchers with deep semantic AI reasoning, the platform reduces the false alarm rate to an exceptional 4.3%, compared to over 52% in legacy tools. The novel dual-AI failover engine successfully combines the sub-second speed and low cost of Groq LLaMA-3-70B with the massive context capacity of Google Gemini 1.5 Pro, ensuring uninterrupted scanning resilience across large enterprise codebases.

[314] [w:p] [style:] [drawing:no]
In comprehensive evaluations across diverse production codebases and web applications, VulnixAI successfully identified 110 vulnerabilities across a representative application codebase (7 Critical, 19 High, 64 Medium, 20 Low) with zero manual setup. Crucially, the platform closed the loop between detection and remediation by automatically authoring, syntax-verifying, and raising 110 pull requests on GitHub, demonstrating an end-to-end automated security pipeline that fundamentally transforms how software vulnerabilities are identified, monitored, and fixed.

[315] [w:p] [style:] [drawing:no]
The system also satisfies the two practical constraints that were treated as design requirements from the outset. It is fully explainable, because every quantity it reports is a directly measurable physical property of the scene and the composite score is a linear combination of those quantities, so the exact percentage contribution of each factor to every alert is available to the operator without any post-hoc attribution method. And it runs on ordinary hardware, sustaining 7.4 frames per second at VGA resolution on an Intel Core i7 processor with no graphics accelerator, which places it within reach of the equipment already installed at typical surveillance sites.

[316] [w:p] [style:] [drawing:no]
The limitations are equally clear and are stated in Section 6.7. The benchmark is small at one hundred and eighty seconds of annotated footage, and the resulting fold-to-fold variance means the absolute figures should be read as indicative. Speed measured in  pixels per frame is camera-dependent, so thresholds require site-specific calibration. Detection recall degrades under severe occlusion beyond roughly six persons per square metre. Cameras are processed independently. Within those bounds, however, the work demonstrates a human-interpretable crowd-risk scoring system that detects the hazard conventional methods miss, raises no false alarms on normal footage, provides a useful early warning margin, and requires no specialised hardware.
