[170] p | blips: [] | text: "4.3.1  Repository Ingestion and Intelligent File Prioritization Scoring"
[171] p | blips: [] | text: "When a user signs in via GitHub OAuth 2.0 and selects a target repository, VulnixAI immediately initiates recursive tree ingestion using the GitHub REST API. In an enterprise repository comprising hundreds or thousands of source files, analyzing every file sequentially with equal weighting is computationally wasteful and mathematically impossible within standard LLM context budgets. To solve this bottleneck, VulnixAI formulates an intelligent AST-guided prioritization scoring function."
[172] p | blips: [] | text: "Let R denote the set of all source code files in the repository, R = {f_1, f_2, ..., f_n}. For each file f_i in R, an Abstract Syntax Tree (AST) is generated to extract structural metrics. The priority score S_priority(f_i) is defined as a linear weighted combination of four normalized security factors:"
[173] p | blips: [] | text: "S_priority(f_i) = w_k * K_sec(f_i) + w_e * E_entry(f_i) + w_r * R_route(f_i) + w_s * S_size(f_i)"
[174] p | blips: [] | text: "where K_sec(f_i) in [0, 1] represents the normalized density of security-sensitive keywords (e.g., 'password', 'token', 'secret', 'exec', 'eval', 'dangerouslySetInnerHTML', 'SELECT', 'query'); E_entry(f_i) in {0, 1} is a binary indicator denoting whether f_i is an application entry point (such as 'index.ts', 'server.js', 'main.py', or 'App.tsx'); R_route(f_i) in [0, 1] quantifies the ratio of public HTTP route definitions and API controllers within the file; and S_size(f_i) in [0, 1] is an inversely scaled file-size penalty favoring compact, high-density files over vast auto-generated bundles. The weighting coefficients satisfy w_k + w_e + w_r + w_s = 1.0, with default empirical weights set to w_k = 0.35, w_e = 0.25, w_r = 0.25, and w_s = 0.15. Files are sorted in descending order of S_priority, ensuring that critical attack surfaces are audited first."

[177] p | blips: [] | text: "4.3.2  Multi-Pass Batching and Context-Window Truncation Algorithm"
[178] p | blips: [] | text: "Once files are prioritized, they must be partitioned into discrete inference batches that fit comfortably within the context window C_max of the primary language model. Let T(f_i) denote the token count of file f_i computed via Byte-Pair Encoding (BPE) tokenization. A naive greedy algorithm that packs files until sum(T(f_i)) &lt;= C_max risks straddling semantic boundaries or starving low-priority files."
[179] p | blips: [] | text: "VulnixAI introduces a multi-pass batching strategy with intelligent semantic truncation. A dynamic token threshold T_budget = gamma * C_max is enforced (with safety margin gamma = 0.75). Files whose token length exceeds an upper ceiling T_single_max (set to 4,000 tokens) undergo AST-aware structural truncation: import statements, interface definitions, exported route signatures, and function headers are preserved, while repetitive boilerplate and static asset definitions are pruned. Consecutive prioritized files are aggregated into a batch B_k = {f_{k,1}, ..., f_{k,m}} such that the total prompt tokens plus anticipated completion tokens remain strictly bounded by T_budget. Batches are dispatched asynchronously to the AI layer, with deduplication hashes computed across findings."

[183] p | blips: [] | text: "4.3.3  Dual-AI Inference and Dynamic Failover Mechanism"
[184] p | blips: [] | text: "To guarantee operational high availability and eliminate single-provider vulnerability, VulnixAI implements a stateful dual-AI failover engine. The primary inference engine utilizes Groq's Language Processing Unit (LPU) architecture running Meta's LLaMA-3-70B-Instruct model. Groq delivers exceptional inference throughput (exceeding 250 tokens per second) at minimal operational expense, enabling sub-second vulnerability analysis per file batch."
[185] p | blips: [] | text: "However, if Groq returns an HTTP 429 (Rate Limit Exceeded), an HTTP 503 (Service Unavailable), experiences an API timeout tau &gt; 12.0 seconds, or if a monolithic file cannot be segmented without losing critical semantic cross-file context, the failover dispatcher instantly intercepts the request. The dispatcher transfers execution seamlessly to Google Cloud's Gemini 1.5 Pro model, which boasts a million-token context window capable of ingesting the entire un-truncated repository in a single forward pass. State transitions are governed by a circuit-breaker pattern: after three consecutive primary failures, the circuit trips to Open state, routing all traffic to the secondary model for an exponential backoff period before attempting a half-open probe."

[188] p | blips: [] | text: "Every potential vulnerability returned by the AI inference layer undergoes rigorous triaging through VulnixAI's multi-factor severity scoring engine. [189] p | blips: [] | text: "R_sev = alpha * K_kw + beta * C_CWE + gamma * E_exploit + delta * I_impact"
[190] p | blips: [] | text: "where K_kw in [0, 100] represents keyword-level risk confirmation; C_CWE in [0, 100] is the baseline Common Weakness Enumeration severity mapped from the official MITRE and CVSS v3.1 databases (e.g., CWE-798 Hardcoded Credentials = 85, CWE-89 SQLi = 95, CWE-79 XSS = 65, CWE-200 Information Exposure = 70); E_exploit in [0, 100] measures exploitability based on route accessibility (public endpoint vs internal helper); and I_impact in [0, 100] quantifies the potential damage to data confidentiality, integrity, and system availability."
